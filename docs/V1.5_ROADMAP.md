# InsureAI v1.0 → v1.5 技术/产品实施路线图

> 基线：`insureai` 分支 `3b305b6`（benchmark v1.0 锁定）+ `27d9ecb`（audit ledger 契约修复）。
> 定位：从「Intelligence Engine 原型 / Beta（≈75 分）」推进到「可支撑保险专业人员日常决策的情报产品（目标 90+）」。
> 本文档把外部评估的 P0/P1/P2 建议逐条落到具体 Issue、数据 Schema、代码模块、测试指标与验收标准。

---

## 一、基线核校：评估结论与代码事实的对齐

制定路线图前，先对评估的关键论断逐一核校（基于当前代码实测）：

| 评估论断 | 代码事实 | 结论 |
|---|---|---|
| Claim 层是最大结构性缺口（60 分） | `claims.py::extract_claims()` 只产出 4 种机械类型（event/entities/numeric/date）；无 supporting/contradicting evidence、无 verification_status；**生产数据实测 1453 个 claim 全部 unverified，cross_checked=0**——证据匹配在真实数据上几乎不生效 | ✅ 证实，且比评估更严重 |
| Evidence 只回答"来源在哪"，不回答"支持了什么" | `attach_evidence()` 是数字/实体/日期集合交集匹配，证据只记录文章元数据，无 support/conflict 方向 | ✅ 证实 |
| 无 Source Hierarchy | `source_authority` 是 0-100 连续值，仅进入 event 级 confidence；trust.py 与 claims.py 均不使用；无 tier 概念 | ✅ 证实 |
| 缺 False Split 指标 | `benchmark.py::pair_metrics()` 只有 precision/recall/false_merge_rate；fixture 无 split 标注字段 | ✅ 证实 |
| Radar"只是统计新闻"（70 分） | `radar.py::build_topic_trends()` 输入是**事件级**（非文章级），7 天窗口 delta 判向；缺 velocity/acceleration/persistence 与 event cluster | ⚠️ 部分修正：已是事件级，缺口在趋势动力学 |
| Decision Guardrail 成熟（85-90 分） | urgency=now 门禁完整（score≥82 + trust=high + accelerating + 无冲突/复核/低证据）；但 `decision_build.py` 硬编码 `role='executive'`，8 角色映射表从未分发；无 Business Impact 等决策上下文字段 | ⚠️ 部分修正：门禁成熟，缺口在角色分发与上下文 |
| KG 是展示非推理（65 分） | 代码支持 8 种节点（含 Claim/Evidence）与 8 种关系，但 **knowledge_graph.json 为空图**（KG workflow 的路径触发器依赖 intelligence.json/claims.json，而它们因 analyze 任务失败从未入库）；UI 只静态展示前 50 节点 | ⚠️ 修正：代码骨架已备，卡在管道断链（今日已修复） |
| UI 是 Dashboard 不是 Workflow（60 分） | `intelligence.html` 有 Summary/KPI/Radar/Entities/Events/Detail；Event Detail 无 Claim 级展示、无冲突证据区块；Human Review 是标签不是队列 | ✅ 证实 |

**核校中发现的最高优先级问题（评估未覆盖）**：daily-collect 的 analyze 任务自 8 月 21 日起**连续 22 次失败**——audit ledger 契约漂移（workflow 要求 claims.json/executive_terminal.json 入账，`audit_ledger.py` 却从未生成这两个 stage）。后果是整个情报层（intelligence.json、claims.json 等 24 个产物）停止每日发布、KG 图谱恒为空。已于 `27d9ecb` 修复，列为 **P0-0**。

## 二、总体原则（延续 v1.0 发布原则）

1. 不再重构整体架构——Canonical Model（Article → Claim → Evidence → Event → Trend → Insight → Decision）已确立，v1.5 是「能力兑现」而非「架构重建」。
2. 不为修 CI 放宽质量门；benchmark v1.0 已冻结，只允许新增 v2 cases。
3. UI 不得生成 artifact 中不存在的事实；单一来源不得获得独立信源加分。
4. 每个能力项必须同时交付：Schema + 构建模块 + 测试指标 + 验收标准，缺一不算完成。

## 三、P0 —— 把「情报可信度」做深（1-2 个迭代）

### P0-0 恢复情报层每日发布（已完成，保持监控）

- **现状**：`27d9ecb` 修复 claims/executive_terminal 两个 audit stage；本地 CI 校验复现通过（27 stages）。
- **验收**：daily-collect analyze 任务连续 3 个调度周期 success；`intelligence.json`/`claims.json` 入库；KG workflow 被路径触发且 `knowledge_graph.json` 非空。
- **防回归**：audit ledger 覆盖测试已锁定契约（`tests/test_audit_ledger.py`）；后续新增 analyze 产物时必须同步 `audit_ledger.py::STAGES`、workflow required 集与测试三方。

### P0-1 Claim Intelligence：让 Claim 成为真正的一等对象（已完成，保持监控）

- **现状**：claim 只是事实片段（实体/数字/日期清单），无结构化命题；生产数据全 unverified。
- **落地结果**：`claims.py` 重写为命题抽取器（Claim Schema v3，含 claim_type/subject/object/value/supporting_evidence/contradicting_evidence/verification_status/first_seen）；新增 `source_tiers.py` 四级来源分层（监管→国际通讯社→行业媒体→博客）驱动 confidence 加权，单源封顶 65；claim 级冲突检测（同命题不一致值标 conflicted）并进 review_queue（`claim_conflict` reason，优先级 +40）；知识图谱新增 SUPPORTS/CONTRADICTS 边与 source_tier 元数据；UI 渲染命题类型标签、置信度与冲突计数。真实数据实测：1486 事件 → 2012 条命题（proposition_coverage 100%），cross_checked 22、conflicted 9（如 "$3.34bn vs 3.35bn" 损失金额矛盾被自动捕获），7 个冲突事件入复核队列。
- **Issue 拆解**：
  - `CLAIM-1` 命题级 Claim Schema（v3）：

    ```text
    claim_id            evt_xxx/c{n}
    event_id            归属事件
    claim_type          transaction_amount | acquisition_intent | regulatory_action |
                        product_launch | rating_change | executive_change | forecast | ...
    claim_text          自然语言命题（一句话，可判定真伪）
    subject / object    主体/客体实体（从 event.entities 结构化）
    value               数值/日期等可验证值（若有）
    source_articles     支持该命题的 article_id 列表
    supporting_evidence [evidence_id, ...]（含 support_strength）
    contradicting_evidence [evidence_id, ...]
    confidence          0-100（重算，见 CLAIM-3）
    verification_status unverified | single_source | cross_checked | conflicted
    first_seen / last_confirmed  时间线
    ```

  - `CLAIM-2` 命题抽取器：基于 event_type × 模板（收购→意图/金额/范围/战略含义；监管→发布方/要求/生效时间…），改造 `claims.py::extract_claims()`；输出进 `claims.json`（version 3），`contract.py::ARTIFACT_VERSIONS` 同步。
  - `CLAIM-3` confidence 重算：现公式 `40 + 25×min(evidence_count,2) + 10×max(domains-1,0)` 忽略来源权威度且同域两文可到 90 分；改为 `来源tier加权 × 独立域数 × 支持方向`，单源封顶 65。
  - `CLAIM-4` 冲突检测：复用 `trust.py` 已有 numeric/entities 冲突逻辑，下沉到 claim 级——同 claim 的证据给出不一致值时标 `conflicted` 并入 review_queue。
- **测试指标**：新增 `claim_proposition_coverage`（事件→命题抽取覆盖率 ≥ 0.8）；`claim_conflict_recall`（标注冲突样本召回 ≥ 0.9）。
- **验收**：Munich Re 收购类事件能拆出 ≥3 条独立命题（意图/金额/范围），每条带独立证据链；`claims.json` v3 通过 schema 校验并进入 audit ledger。

### P0-2 Evidence Graph：从 Source List 到证据关系（已完成，保持监控）

- **现状**：`attach_evidence()` 集合交集匹配，证据无方向。
- **落地结果**：证据三向完备（`relation: support | contradict | context`，均带 `matched_span` 命中片段与 source_tier）；**匹配率根因修复**——`_infer_category` 不再盲从上游 event_type，命题模板必须有动作词佐证（话题层 capital_reinsurance 分类与命题层"融资"动作解耦，资本规模预测/定价评论不再被误套融资模板产出假命题）；`claims.json` 顶层新增生产指标 `claim_evidence_match_rate`，`evaluation_metrics.py` 新增 `production_claim_metrics()`（fail-closed：产物缺失按 0 分），CI gate 两处断言 `≥ 0.6`。真实数据实测：match_rate **76.6% → 99.9%**（unverified 471 → 2，剩余 2 条为 subject 抽取噪声且有 context 证据兜底），KG SUPPORTS 边 1591 → 2097，复核队列因误报减少从 558 精简至 192 项（claim_conflict 7 项保留）。
- **Issue 拆解**：
  - `EVG-1` 证据方向：evidence 记录增加 `relation: support | contradict | context` 与 `matched_span`（命中片段），改造 `claims.py::attach_evidence()` 为按 claim_type 的定向匹配（金额 claim 匹配金额上下文，而非任意数字）。
  - `EVG-2` 匹配率修复（最痛点）：生产 1453 claim 全 unverified 说明现匹配在真实中文标题+摘要上失效。要求：中文/英文分别归一化（全半角、单位、货币符号），匹配从 title+summary 全文进行；**新增生产指标 `claim_evidence_match_rate ≥ 0.6`**，进 quality gate。
  - `EVG-3` KG 直连：Evidence 方向边（SUPPORTS/CONTRADICTS）已在 `knowledge_graph.py` REL_TYPES 中，打通后 KG 自动获得证据图。
- **测试指标**：`claim_evidence_match_rate`（生产数据）；`single_source_false_cross_check_rate` 保持 0。
- **验收**：任一 Event Detail 可答"该命题有几个证据、各来自哪、有没有反方证据"。

### P0-3 Source Authority Tier：来源层级制度化（已完成，保持监控）

- **现状**：`source_authority` 连续值，未进 trust/claim；无 tier。
- **落地结果**：四级层级在 `contract.py::SOURCE_TIERS` 单一定义（label/authority/trust_weight，SRC-1），`source_tiers.py` 只负责 domain/source_type → tier 映射，trust/claims/intelligence 三处共用不可漂移。**trust.py::assess() 层级加权**（SRC-2）：source_score 由最佳来源层级驱动（T1=100/T2=89/T3=75/T4=62 + 域多样性加成 ≤15），两条制度化规则——Tier1 单源保底 medium（score≥62）、无 T1/T2 来源封顶不得 high（score≤78，行业媒体互相印证不能替代一手来源）；trust 新增 `best_source_tier`/`tier_profile`，evidence 行携带 `source_tier`。**intelligence.py authority 换算**：声明值与 tier 基准 6:4 混合，生产数据无声明值时完全由 tier 驱动（此前所有来源统一默认 70）。**UI 徽章**（SRC-3）：trust-ui.js 证据列表逐条展示 T1 绿/T2 蓝/T3 灰/T4 橙徽章与事件最高来源层级。指标 `tier1_single_source_trust`/`tier3_pair_not_high` 进 `source_authority` 区块并纳入 macro_quality（12 项 → 14 项）。生产实测：tier 分布 T1×8 / T2×19 / T3×1418 / T4×41，trust 分布与升级前一致（high 0 / medium 1481 / low 5）——旧行为本就保守，新规则把"high 必须有一手或通讯社来源"从巧合变成制度。
- **Issue 拆解**：
  - `SRC-1` 在 `contract.py` 定义 4 级 Tier（Tier1 监管/政府/交易所/公司公告/法院；Tier2 Reuters/Bloomberg/FT/WSJ；Tier3 行业媒体与专业研究机构；Tier4 博客/转载/聚合/社交），映射函数 domain → tier。
  - `SRC-2` tier 进入三处：`trust.py::assess()`（Tier1 单源可授予 medium 而非 low；两个 Tier3 来源不等于一个 Tier1+公告）、claim confidence（P0-1）、`intelligence.py` authority 换算。
  - `SRC-3` UI 徽章：Event Detail 证据列表展示 tier 徽章。
- **测试指标**：`tier1_single_source_trust`（Tier1 单源事件 trust ≥ medium 的正确率）；`tier3_pair_not_high`（两个 Tier3 来源不得得 high trust）。
- **验收**：`2 个行业媒体` 与 `监管文件+公司公告` 在 Trust/Claim confidence 上可区分。

### P0-4 False Split 指标 + 专业 Event Detail（已完成，保持监控）

- **现状**：无 split 检测；Event Detail 无 Claim/冲突区块。
- **落地结果（FS-1）**：根因在 `intelligence.py` 聚类的 anchor 冲突硬阻断——主动/被动语态使 tags 首位主实体不同（"Munich Re" vs "At-Bay"），锚点冲突即拒绝合并，同一事件被拆成多条。修复为 `anchor_conflict` 仅在**实体重叠度 < 0.5** 且 score < 0.72 时硬阻断（实体集高度重叠时允许合并），修复本身保守。fixture v2 增 `split_cases` 双用例：`event_split_001`（主动/省略/被动三种表述两两须合并）与 `event_split_guard_001`（同实体不同动作——收购 vs 合作，必须保持拆分，防矫枉过正）。`benchmark.py::split_benchmark()` 计算 `false_split_rate = fn / expected_positive`；`safety_pass` 双门禁（false_split_rate==0 且守卫用例 false_merge_rate==0）；`macro_quality` 8→9 项（阈值仍 0.95）。测试覆盖三表述合并为 1 事件（source_count=3）、守卫保持 2 事件、false_split_rate==0、9 项端到端 macro。生产实测：1486→1485 事件（合并 1 个真实拆分，其余行为不变），benchmark macro_quality=1.0 / safety_pass=true；CI benchmark.yml 汇总输出增 `event_false_split_rate`。
- **落地结果（ED-1）**：`intelligence.html` 事件详情从“元数据列表”重构为六区块决策卡片：What happened（发生了什么 + 为什么重要 + 影响谁 + Signal 条）→ 关键命题（verification_status 四态徽章：已交叉验证/单一来源/证据冲突/待验证 + 置信度 + 支持/矛盾/关联计数 + 独立域数）→ 证据（T1-T4 来源层级徽章 + 支持/矛盾方向标签 + matched_span 原文片段 + 原文链接；命题级证据按 evidence_id 去重合并，方向取最强）→ 冲突证据区（支持 span vs 矛盾 span 双栏对照 + Trust 层冲突字段）→ 建议（decision 的 action/urgency/guardrail + 依据 + 接下来关注）→ Human Review 状态（review_queue.json 的优先级/状态/原因列表，无积压时展示 advisory 边界）。页面加载 review_queue.json 作为第二 artifact；事件列表增“命题冲突”徽章。**UI 契约测试**（`tests/test_event_detail_ui.py`，7 项）：六区块顺序锁定、四态徽章/T1-T4/方向样式齐全、渲染器字段访问 ⊆ 白名单（剥离注释与展开运算符后正则提取）、白名单字段全部在合成 artifact（build + trust + claims + decisions + review_queue 全 hermetic 构造）中存在、复核区块原因来自 artifact。生产数据 node 冒烟：冲突事件/交叉验证事件/复核事件/单源事件四类均六区块完整、无注入、复核原因与 artifact 数量一致。
- **Issue 拆解**：
  - `FS-1` benchmark v2 cases：fixture 增 `split_cases`（同一事件三种表述应合并）；`pair_metrics()` 增 `false_split_rate = fn_split / expected_positive`；纳入 `macro_quality`（8 项 → 9 项，阈值仍 0.95，v1 case 不动）。
  - `ED-1` Event Detail 重构（`intelligence.html` + `intelligence-ui.js`）：What happened → 关键 Claims（含 verification_status 徽章）→ Evidence（tier 徽章 + support/conflict 方向）→ 冲突证据区 → 建议 → Human Review 状态。
- **测试指标**：`false_split_rate == 0`（v2 标注集）；UI 契约测试（detail 区块渲染的字段全部来自 artifact）。
- **验收**：评估中设想的"决策卡片"结构落地，且不引入 artifact 之外的事实。

## 四、P1 —— 趋势引擎与决策上下文（2-3 个迭代）

### P1-1 Trend Intelligence：Radar 升级为趋势引擎（已完成，保持监控）

- **现状**：事件级 7d/7d delta，无动力学指标、无 event cluster。
- **落地结果（TRD-1/2/3）**：`radar.py` 的 `build_topic_trends` 升级——每条趋势新增动力学四指标（`velocity`=7d 环比事件数变化率、`acceleration`=velocity 相对前一窗口的变化（三窗口 0-7/7-14/14-21d）、`persistence`=从最新事件日往前连续活跃天数、`source_diversity`=7d 窗口独立域数）与 TRD-3 解释字段 `why`（四要素：independent_events/sources/days/core_entities + event_ids 可追溯列表）；direction 判定逻辑不变（回归安全）。新建 `trend_intelligence.py` 管道步骤（TRD-1）：30 天窗口内同 topic 事件复用 `intelligence._event_similarity`（单一判定口径）聚为 event cluster（代表元贪心法、相似度>=0.45、代表取组内最早事件保证稳定），产出独立工件 `radar.json`（version 2，contract.ARTIFACT_VERSIONS 单源，`build_radar` 的 version 同源读取防漂移）：topic_trends（含 cluster_ids 关联）+ event_clusters 明细（top 24 by momentum；cluster_ids 关联用全量活跃 cluster，避免 top-N 截断拉低覆盖率）。锁步更新：audit_ledger STAGES（28 stages）、daily-collect analyze 步骤/required/git add、test.yml py_compile。`evaluation_metrics.trend_metrics()` 新增三项指标（不进 macro，14 项保持）：dynamics_correctness、trend_explainability（rising 空列表不默认满分，构造真实 rising 路径）、cluster_unit_precision。hermetic 测试 `tests/test_trend_intelligence.py`（11 项）覆盖动力学数值、persistence 连续性、新主题 velocity、rising 四要素、cluster 聚/分、窗口排除、活跃关联、版本单源、工件结构、rising 全可解释。生产实测：746/746 事件入 726 cluster、177 活跃 cluster 关联 8 topic、产品创新 rising（v=0.435/a=0.583/p=11d/sd=7域，why=33 独立事件/7 来源/持续 11 天）；macro_quality=1.0、375 tests OK。
- **Issue 拆解**：
  - `TRD-1` Event Cluster：topic × entities 相似的事件聚为 cluster（复用 `_event_similarity`），cluster 作为 radar 统计单元，输出 `cluster_id`。
  - `TRD-2` 动力学指标：`velocity`（周环比事件数变化率）、`acceleration`（velocity 的变化）、`persistence`（连续活跃天数）、`source_diversity`（独立域数）；进 `radar.json`（version bump）。
  - `TRD-3` 趋势解释：每条 rising topic 附"为什么"——`n 个独立事件 / m 个来源 / 持续 k 天 / 核心实体`，供 UI 直接渲染。
- **测试指标**：`accelerating_recall`（已有，保持）；新增 `trend_explainability`（每条 rising 均含四要素）。
- **验收**：Radar 能回答"AI 保险为什么在加速"且数据可追溯到事件列表。

### P1-2 Executive Decision Card：从"建议"到"决策上下文"

- **现状**：decision 只有 action+urgency+basis+guardrail。
- **Issue 拆解**：
  - `DEC-1` 决策上下文字段：`business_impact`（战略/产品/核保/投资/合规分面的影响强度 0-100）、`affected_functions`、`potential_opportunity`、`potential_risk`、`what_to_monitor`（从 `insight.what_to_watch` 继承）、`recommended_next_step`；来源全部为 event 已有信号的映射，不得凭空生成。
  - `DEC-2` 角色分发：`decision_build.py` 去掉 `role='executive'` 硬编码，按 `ROLE_ACTIONS` 的 8 角色生成多视角 decision（artifact 按 role 分组），UI 加角色切换。
- **测试指标**：`decision_context_coverage`（高关注事件的决策卡六要素齐备率 ≥ 0.9）；角色分发回归测试。
- **验收**：同一事件，CEO 看到战略影响与监控点，核保看到风险暴露——数据同源、视角不同。

### P1-3 Knowledge Graph：从展示到查询

- **现状**：代码骨架完整（8 节点/8 关系），断链已修复；UI 静态前 50 节点。
- **Issue 拆解**：
  - `KG-1` 基础查询 API（纯前端亦可）：`knowledge-graph.html` 增实体搜索 + 90 天时间窗过滤 + 邻居展开。

- **测试指标**：`kg_nonempty_gate`（node_count > 0 作为 daily-collect 门禁）；查询正确性用例测试。
- **验收**：图谱非空且有持续数据；两个预置查询可答。

### P1-4 真实数据标注基准（benchmark v2）

- **现状**：全部指标基于构造 fixture（且全为完美值 1.0/0.0）；三套评测（benchmark.py 8 指标 / evaluation_metrics.py 10 指标 / evaluation.py 4 case）指标集已漂移。
- **Issue 拆解**：
  - `BM-1` 标注集：从生产数据抽样 100 events / 500 articles，人工标注同事件对/异事件对/关键 claim；存 `benchmarks/v2/`，遵守"生产数据不能直接成为 expected output，需人工审阅标注"。
  - `BM-2` 指标统一：三套评测收敛到单一指标注册表（`evaluation_metrics.py` 为准），`benchmark.py` 引用之，消除漂移。
  - `BM-3` 真实数据门禁：`production_replay.py` 从"稳定性"扩展为带标注子集的质量评分（先报告后门禁）。
- **测试指标**：v2 集上 event precision/recall、false_merge、false_split、claim accuracy 首次有真实基线值。
- **验收**：算法改动可在真实分布上量化比较，而非只在小样本完美 fixture 上。
